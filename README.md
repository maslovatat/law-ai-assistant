# Сопровождение юридических дел — интерактивный прототип

Демонстрационный frontend-прототип платформы сопровождения юридических дел: от описания
ситуации до подготовки документов, разбора ответа контрагента и передачи дела юристу.

Прототип создаётся, чтобы показать заказчику модель взаимодейения с продуктом: как
пользователь начинает дело, как AI собирает факты и объясняет свои предложения, как
система показывает текущее состояние дела и что делать дальше.

---

## ⚠️ Важно: это прототип, а не юридическая система

* Все данные, документы, сообщения, ответы контрагентов, решения AI и решения юриста —
  **синтетические mock-данные**.
* **Настоящей авторизации нет.** Роль переключается демонстрационным переключателем.
* **Реальной отправки документов нет.** «Имитировать отправку» — симуляция: интерфейс
  прямо сообщает, что реальный документ не был передан.
* **Настоящий LLM не используется.** Ответы AI — заранее подготовленные сценарии.
* Реальных персональных данных, API-ключей и секретов в проекте нет.
* Предложения AI — **возможные варианты действий**, а не юридическое заключение.
  Прототип намеренно не создаёт впечатления гарантированного результата.

## Стек

| Слой            | Решение                                                    |
| --------------- | ---------------------------------------------------------- |
| Сборка          | Vite 6                                                     |
| UI              | React 19 + TypeScript 5.8                                  |
| Маршрутизация   | react-router-dom 7, `HashRouter` (совместимо с GH Pages)   |
| Состояние       | React Context + `useReducer`                               |
| Стили           | собственный CSS с дизайн-токенами (без UI-кита)            |
| Тесты           | скрипты проверки на esbuild + `react-dom/server`           |

Зависимостей минимум: нет Redux, нет UI-кита, нет ORM, нет тестового раннера с
отдельной конфигурацией.


## Деплой на GitHub Pages

Приложение не требует backend: это статические файлы, а маршрутизация построена на
`HashRouter`, поэтому серверные rewrite-правила не нужны.

```bash
npm run build
npm run deploy          # публикует ./dist в ветку gh-pages
```

Затем в репозитории: **Settings → Pages → Source → Deploy from a branch → `gh-pages` / root**.

Если публикация выполняется вручную, скопируйте содержимое `dist` в корень ветки
`gh-pages`. Путь к assets задан относительным (`base: "./"` в `vite.config.ts`), поэтому
прототип работает и по адресу `https://<user>.github.io/<repo>/`.

## Демонстрационные дела

### LC-2026-001 — «Возврат денежных средств за неисправный товар»

Основной сценарий, категория «Защита прав потребителей». Открывается уже на этапе
проверки юристом, чтобы можно было сразу посмотреть карточку дела, факты, документы,
историю и интерфейс юриста.

Тот же сценарий можно пройти с нуля: **«Новое дело» → шаблон основного дела → AI-интервью**.

### LC-2026-002 — «Противоречие в данных о покупке»

Дата покупки в сообщении пользователя (10.08.2026) не совпадает с датой в чеке
(12.08.2026). Система показывает оба источника и **не выбирает значение
самостоятельно**: уточнение остаётся за пользователем или юристом.

Этот сценарий можно получить и в основном demo-case: в интервью на вопрос «Когда был
приобретён товар?» выберите **10.08.2026** — противоречие обнаружится автоматически.

## Роли

Роль переключается в шапке приложения.

**Пользователь** — «Мои дела», карточка дела с вкладками
«Обзор → AI → Факты → Документы → История».

**Юрист** — «Очередь дел» и карточка дела с вкладками
«Обзор → Факты → Документы → Проверка → Общение → История».

Юрист видит контекст дела целиком: краткое описание, полную историю, факты с источниками,
все документы, ответ контрагента, отдельно оформленное **предложение AI**, проблемные
места, переписку с пользователем и **своё решение** (визуально отличается от AI).

## Основной demo-flow

```text
Landing
  ↓ Новое дело → описание ситуации
AI-интервью (подготовленные вопросы и варианты ответов)
  ↓
Факты и источники: «Пользователь сообщил» vs «Подтверждено документом»
  ↓
Возможные варианты (3 карточки с основаниями)
  ↓ Попробовать мирное решение → задача «связаться с продавцом»
  ↓ Сообщить результат → «Продавец отказался»
Новый анализ ситуации
  ↓ Подготовить претензию → проверка данных (что есть / чего не хватает)
Проект претензии в mock-просмотрщике + список использованных фактов
  ↓ Подтвердить
Чеклист перед отправкой → «Имитировать отправку» (явно помечено как симуляция)
  ↓
Ожидание ответа продавца (срок, ответственный)
  ↓ Сообщить о полученном ответе
Ответ продавца → «Ответ не удовлетворяет»
  ↓
Подготовка судебного продолжения (список данных: есть / необходимо получить)
  ↓ Передать дело юристу
Кабинет юриста → очередь дел
  ↓ Карточка дела
Запрос дополнительной информации → ответ пользователя → факт обновлён
  ↓
Решение юриста (отдельно от предложения AI)
```

Альтернативные ветви, доступные в интерфейсе:

* «Продавец согласился решить проблему» — дело закрывается как решённое;
* «Срок истёк, ответа нет» — дело переходит в состояние ожидания решения пользователя;
* «Закрыть дело» — доступно на любом этапе, с подтверждением и сохранением в истории;
* повторный запуск интервью для дополнения сведений.

### Как устроена модель состояний

Состояние дела описывается данными, а не ветвлениями по номеру дела:

```text
Case.stage          основной этап (14 состояний)
Case.flags[]        дополнительные признаки: требуется юрист, ожидаем пользователя,
                    ожидаем контрагента, требуется уточнение, обнаружено противоречие,
                    ошибка отправки, срок требует проверки
Case.expectedEvent  что ожидается, кто ответственный, есть ли срок
Case.outcome        итог дела и причина
```

`src/lib/workflow.ts` выводит доступные действия из этапа, флагов и ожидаемого события.
Логика одинакова для всех дел, поэтому демонстрационные дела можно заменить или
дополнить без изменения переходов.

### Факты и источники

Факт и его источник — разные сущности. У каждого факта есть состояние:

```text
UNCONFIRMED             не подтверждено
CONFIRMED_BY_USER       подтверждено пользователем
CONFIRMED_BY_DOCUMENT   подтверждено документом
CONFLICT                противоречие
REQUIRES_LAWYER         требуется проверка юриста
```

Если источники расходятся, сохраняются оба варианта со своими источниками, а факт
получает состояние `CONFLICT`. Система не выбирает значение автоматически.

### Замена mock-слоя на реальный API

Логика переходов собрана в mock-сервисах `src/lib/mock/` (`applyAction`, `deriveFacts`,
`applyLawyerDecision`) и возвращает новое состояние дела. Чтобы подключить реальный
backend, достаточно заменить реализацию сервиса и хранилище состояния: UI-компоненты
менять не потребуется.

## Что намеренно не реализовано

Backend, база данных, настоящая авторизация, реальные LLM API, OCR, настоящая обработка
документов, электронная подпись, интеграции с судами и государственными системами,
реальная отправка юридически значимых документов, production workflow engine, реальные
юридические расчёты сроков.
