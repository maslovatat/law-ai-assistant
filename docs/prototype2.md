# Задание для ИИ-агента: UI-прототип сервиса отправки досудебных претензий через Почту России

## 1. Цель проекта

Разработать интерактивный веб-прототип сервиса, позволяющего пользователю отправлять уже подготовленные досудебные претензии посредством электронного заказного письма Почты России через ИС ЭПС.

Пользователь должен иметь возможность:

1. Загрузить готовую претензию в формате PDF.
2. Указать отправителя и получателя.
3. Проверить данные и состав отправления.
4. Имитировать подтверждение отправки.
5. Просматривать историю отправлений и демонстрационные статусы доставки.

**В рамках текущей задачи реализуется только frontend.** Backend, реальная отправка писем, интеграция с API Почты России, платежи, авторизация через внешние сервисы и криптографические операции не реализуются.

Прототип должен выглядеть как законченный MVP реального SaaS-продукта, а не как набор отдельных статичных экранов.

## 2. Контекст и ограничения предметной области

Сервис не является конструктором юридических документов. Предполагается, что пользователь уже подготовил претензию самостоятельно или получил её из другой системы.

Основной сценарий:

- загрузить готовый PDF;
- указать адресата;
- проверить реквизиты;
- подтвердить отправление;
- получить демонстрационное подтверждение операции;
- отслеживать дальнейшие изменения статуса.

Целевая интеграция — ИС ЭПС Почты России, предназначенная для электронных заказных писем.

Документация для изучения предметной области:

- Памятка API отправителя ИС ЭПС: https://www.pochta.ru/assets/Pamyatka_API_otpravitelya_IS_EPS_cfa50e1b73.pdf
- Официальная документация API «Отправка»: https://otpravka.pochta.ru/specification
- Официальная документация API отслеживания: https://tracking.pochta.ru/specification

При реализации UI необходимо учитывать различие между ИС ЭПС и API сервиса «Отправка». Не переносить механически поля, статусы, методы авторизации или ограничения одного API на другой.

Если точные возможности ИС ЭПС не подтверждены документацией, использовать нейтральные названия полей и демонстрационные значения. Не придумывать реальные методы API, форматы запросов, тарифы, статусы или требования к электронной подписи.

## 3. Технологический стек

Если репозиторий уже содержит приложение, сначала изучить его архитектуру, package.json, существующие компоненты, соглашения и инструкции проекта. По возможности использовать имеющийся стек и не переписывать приложение без необходимости.

Если проект пустой, использовать:

- React;
- TypeScript;
- Vite;
- Tailwind CSS;
- shadcn/ui для базовых компонентов интерфейса;
- React Router для маршрутизации;
- Lucide React для иконок.

Для форм использовать React Hook Form и Zod, если они совместимы с текущим проектом.

Для локального хранения допустимо использовать localStorage. Не сохранять в нём содержимое реальных пользовательских претензий, персональные данные или содержимое загруженных документов без явной необходимости. В прототипе предпочтительно использовать синтетические данные.

Не устанавливать дополнительные библиотеки без необходимости.

## 4. Общие требования к дизайну

Создать современный, минималистичный интерфейс юридического SaaS-сервиса.

Визуальный стиль:

- светлая тема;
- белый или светло-серый фон;
- сдержанная синяя цветовая палитра;
- достаточное количество свободного пространства;
- аккуратные карточки с умеренным скруглением;
- понятная визуальная иерархия;
- единая система отступов, размеров и типографики;
- заметные основные действия;
- отсутствие избыточных градиентов, декоративных анимаций и визуального шума.

Интерфейс должен быть адаптивным. Основной сценарий ориентирован на десктоп, но базовые действия должны быть доступны на мобильных устройствах.

Использовать русский язык во всех пользовательских интерфейсах, уведомлениях, формах и демонстрационных данных.

Все основные экраны должны выглядеть как части одного приложения.

## 5. Структура приложения

Реализовать следующие страницы:

1. Главная панель.
2. Создание отправления — мастер из нескольких шагов.
3. Проверка отправления.
4. Результат отправки.
5. Список отправлений.
6. Карточка конкретного отправления.
7. Список черновиков.
8. Профиль и настройки отправителя.

Предусмотреть боковую навигацию на десктопе и адаптированную навигацию на мобильных устройствах.

Основные пункты меню:

- Главная;
- Новая отправка;
- Отправления;
- Черновики;
- Профиль.

Маршруты должны работать при прямом открытии соответствующей страницы и обновлении браузера.

## 6. Главная панель

Главная страница должна содержать:

- приветственный заголовок;
- основную кнопку «Отправить претензию»;
- краткое объяснение принципа работы сервиса;
- карточки с количеством отправлений и черновиков;
- список последних отправлений;
- текущие демонстрационные статусы;
- ссылку на просмотр всех отправлений.

Для первого запуска предусмотреть несколько синтетических отправлений с различными статусами.

Примеры статусов:

- Черновик;
- Подготовлено;
- Отправляется (демонстрация);
- Принято системой;
- В пути;
- Вручено;
- Требует внимания.

Эти статусы являются состояниями UI-прототипа. Не выдавать их за точный перечень кодов или статусов ИС ЭПС.

Если список пуст, показывать аккуратное пустое состояние с предложением создать первое отправление.

## 7. Мастер создания отправления

Мастер состоит из четырёх шагов.

### Шаг 1. Загрузка документа

Заголовок: «Загрузите готовую претензию».

Добавить:

- область Drag & Drop;
- кнопку выбора файла;
- название и формат файла;
- размер файла, если он доступен;
- возможность удалить или заменить файл;
- индикатор успешного добавления;
- сообщение об ошибке при недопустимом файле.

Для реальной работы UI предусмотреть выбор локального PDF через input type="file".

Требования к проверке:

- разрешать только PDF;
- проверять MIME-тип и расширение;
- показывать понятную ошибку при выборе неподдерживаемого файла;
- предусмотреть разумное ограничение размера файла как настраиваемую константу, не выдавая его за официальный лимит Почты России;
- запрещать переход к следующему шагу без документа.

Не реализовывать загрузку файла на сервер.

По возможности показывать предпросмотр PDF средствами браузера. Если это невозможно, отображать карточку файла и информативную заглушку предпросмотра.

В прототипе не требуется распознавание текста или автоматическое извлечение реквизитов из PDF.

### Шаг 2. Отправитель и получатель

Создать форму с двумя логическими блоками.

**Отправитель:**

- тип отправителя;
- ФИО или наименование организации;
- дополнительные реквизиты при необходимости;
- контактный адрес электронной почты для уведомлений.

**Получатель:**

- тип получателя: физическое лицо или организация;
- ФИО либо наименование организации;
- почтовый индекс;
- регион;
- населённый пункт;
- улица;
- дом;
- корпус или строение;
- квартира или офис, если применимо.

Требования:

- предусмотреть переключение типа получателя;
- адаптировать поля под выбранный тип;
- валидировать обязательные поля;
- показывать ошибки рядом с соответствующими полями;
- сохранять введённые значения при переходах между шагами;
- предусмотреть возможность возврата и редактирования данных.

Не утверждать, что адрес проверен Почтой России. До интеграции допускается только локальная проверка заполненности и формата.

### Шаг 3. Проверка отправления

Показать сводку:

- имя файла;
- формат документа;
- отправитель;
- получатель;
- полный почтовый адрес;
- предупреждения о незаполненных или потенциально некорректных данных.

Предусмотреть переход к редактированию каждого блока.

Показывать информацию о том, что точные тарифы, допустимость отправления и требования к подписи определяются после подключения к ИС ЭПС.

Не показывать выдуманную стоимость отправки. Если стоимость не рассчитывается, явно написать: «Стоимость будет определена после подключения к Почте России».

Перед подтверждением пользователь должен установить чекбокс о том, что он проверил данные и прикладываемый документ.

Не создавать впечатление, что чекбокс заменяет электронную подпись или иное юридически значимое подтверждение.

### Шаг 4. Демонстрационная отправка

После подтверждения показать состояние обработки отправления.

Реальную отправку не выполнять.

Сымитировать последовательность состояний интерфейса:

1. «Подготавливаем отправление».
2. «Обрабатываем запрос».
3. «Демонстрационная операция завершена».

Переходы должны быть реализованы на клиенте. Не создавать длительные искусственные задержки.

После завершения показать экран результата с заметным указанием «Демонстрационный режим. Письмо не отправлено».

Номер отправления, квитанция и история событий могут использоваться только как синтетические данные, явно помеченные как демонстрационные.

При успешном завершении добавить запись в локальное состояние списка отправлений. Сохранять демонстрационные записи между обновлениями страницы допустимо.

При повторном нажатии кнопки нельзя создавать дубликаты одного и того же демонстрационного отправления.

## 8. Список отправлений

Создать страницу со списком всех демонстрационных отправлений.

Каждая запись должна содержать:

- получателя;
- дату создания;
- название документа;
- текущий статус;
- условный идентификатор отправления;
- ссылку на подробную карточку.

Добавить:

- поиск по получателю и названию документа;
- фильтрацию по статусу;
- сортировку по дате;
- понятное пустое состояние;
- адаптивное отображение таблицы или карточек.

Фильтры и поиск должны реально работать на клиенте.

Не использовать случайные статусы, меняющиеся при каждом рендере. Данные должны быть детерминированными.

## 9. Карточка отправления

Создать отдельную страницу для просмотра одного отправления.

Показывать:

- идентификатор демонстрационной записи;
- документ;
- получателя;
- адрес;
- отправителя;
- дату создания;
- текущий статус;
- историю событий;
- доступные действия.

Предусмотреть визуальную временную шкалу.

Пример демонстрационной истории:

- Документ добавлен.
- Данные получателя заполнены.
- Отправление проверено.
- Демонстрационная операция завершена.

Для тестовых отправлений с условным статусом доставки можно отображать события «Принято», «В пути» и «Вручено», но обязательно помечать их как демонстрационные.

Предусмотреть кнопку возврата к списку.

Не создавать поддельную официальную почтовую квитанцию, которую можно принять за реальный документ Почты России. Вместо этого можно сформировать собственную страницу-резюме с явной пометкой «Демонстрационный документ».

## 10. Черновики

Реализовать список незавершённых отправлений.

Пользователь должен иметь возможность:

- открыть черновик;
- продолжить заполнение;
- удалить черновик после подтверждения;
- видеть дату последнего изменения;
- видеть этап, на котором остановился процесс.

Черновик должен сохранять состояние мастера и введённые демонстрационные данные.

Для демонстрации допустимо сохранять состояние в localStorage. Не включать в исходные демонстрационные данные реальные персональные данные.

## 11. Профиль и настройки

Создать страницу с настройками отправителя.

Поля:

- тип отправителя;
- ФИО или наименование;
- контактная электронная почта;
- почтовый адрес отправителя;
- настройки уведомлений.

Предусмотреть кнопки «Сохранить изменения» и «Отменить».

Изменения должны отражаться в интерфейсе и использоваться при создании нового черновика.

Не реализовывать реальную регистрацию, вход, подтверждение почты или внешнюю авторизацию.

Добавить пояснение, что профиль является локальным демонстрационным профилем.

## 13. Модель данных

Предусмотреть TypeScript-типы примерно следующего назначения:

- `Sender`;
- `Recipient`;
- `DocumentAttachment`;
- `ShipmentDraft`;
- `Shipment`;
- `ShipmentEvent`;
- `ShipmentStatus`.

Сущность отправления должна включать:

- внутренний идентификатор;
- сведения об отправителе;
- сведения о получателе;
- метаданные документа;
- дату создания;
- дату последнего изменения;
- статус;
- историю событий;
- признак демонстрационных данных.

Не сохранять в localStorage содержимое реального PDF. В демонстрационном режиме достаточно хранить метаданные файла.

Если после обновления страницы файл недоступен, показывать понятное сообщение о необходимости загрузить его повторно.

## 14. UX и доступность

Обязательно реализовать:

- адаптивную вёрстку;
- состояния загрузки и обработки;
- сообщения об ошибках;
- валидацию форм;
- подтверждение потенциально разрушительных действий;
- понятные подписи полей;
- видимые состояния фокуса;
- доступность управления с клавиатуры;
- достаточный контраст текста;
- отсутствие горизонтальной прокрутки на мобильных устройствах;
- корректные пустые состояния;
- единообразные кнопки и статусы.

Не использовать `alert()` и `confirm()` в качестве основного интерфейса. Для уведомлений применять toast-компоненты, а для подтверждений — диалоговые окна.

Все кнопки и интерактивные элементы должны выполнять реальное действие внутри прототипа. Не оставлять декоративные кнопки без обработчиков.

## 15. Демонстрационные данные

Подготовить несколько тестовых отправлений с вымышленными получателями и различными состояниями.

Данные должны включать:

- минимум один черновик;
- минимум одно подготовленное отправление;
- минимум одно демонстрационное отправление в пути;
- минимум одно демонстрационное отправление со статусом «Вручено».

На всех страницах обеспечить согласованность данных: изменение или удаление записи должно отражаться в списке, карточке и сводной статистике.

Не использовать настоящие ФИО, адреса, идентификаторы почтовых отправлений или реальные квитанции.

## 16. Что не входит в задачу

Запрещается реализовывать или имитировать реальную интеграцию без соответствующих серверных компонентов.

Вне рамок текущей задачи:

- вызовы API ИС ЭПС;
- вызовы API «Отправка»;
- отправка настоящих писем;
- реальные платежи;
- генерация и хранение криптографических ключей;
- подписание документов электронной подписью;
- хранение закрытых ключей;
- отправка реальных персональных данных;
- настоящая авторизация через Почту России;
- утверждения о юридической значимости демонстрационного подтверждения.

Вместо этого интерфейс должен использовать синтетические данные и ясно указывать, что внешняя интеграция отсутствует.

## 17. Критерии приёмки

Работа считается завершённой, если:

1. Приложение запускается локально по инструкции в README.
2. Все основные страницы доступны через навигацию.
3. Мастер проходит все четыре шага.
4. PDF можно выбрать через файловый диалог, проверить и удалить.
5. Данные отправителя и получателя валидируются.
6. При возврате на предыдущий шаг данные не теряются.
7. Подтверждение создаёт демонстрационную запись отправления.

## 18. Порядок выполнения

**Этап 2. Базовый интерфейс**

Реализуй дизайн-систему, общую навигацию, layout и адаптивную вёрстку.

**Этап 3. Основной сценарий**

Реализуй загрузку PDF, формы отправителя и получателя, проверку отправления и демонстрационный результат.

**Этап 4. Управление отправлениями**

Реализуй список, поиск, фильтрацию, карточку отправления, черновики и профиль.

**Этап 5. Полировка**

Проверь все переходы, ошибки форм, состояния загрузки, сохранение состояния, мобильную вёрстку и визуальную согласованность.

**Этап 6. Проверка**

Запусти TypeScript-проверку, production-сборку и доступные тесты. Исправь ошибки.

- как запустить проект;
- какие проверки выполнены;
