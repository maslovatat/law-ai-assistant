# Задача

Разработать интерактивный frontend-прототип веб-платформы сопровождения юридических дел.

Прототип предназначен для демонстрации заказчику и получения обратной связи перед разработкой полноценного веб-приложения.

Это НЕ production-система.

В рамках задачи не требуется:

* backend;
* база данных;
* настоящая авторизация;
* реальные LLM API;
* OCR;
* реальная обработка документов;
* реальные юридические интеграции;
* реальная отправка документов;
* настоящая электронная подпись.

Все данные, документы, сообщения, ответы контрагентов, решения AI и решения юриста должны быть mock-данными.

---

# 1. Контекст продукта

Основной объект системы — юридическое дело.

Пользователь описывает свою проблему, после чего AI проводит интервью, собирает необходимые сведения и документы, анализирует ситуацию и предлагает возможный способ решения.

В зависимости от ситуации дело может пойти по разным маршрутам:

* пользователь решает проблему самостоятельно;
* мирное урегулирование;
* подготовка и отправка досудебной претензии;
* передача юристу;
* дальнейшее судебное продолжение.

AI является помощником внутри процесса, а не автономным юридическим субъектом.

AI:

* проводит интервью;
* извлекает и структурирует сведения;
* выявляет недостающие данные;
* выявляет противоречия;
* предлагает варианты действий;
* помогает подготовить документы;
* анализирует полученные ответы.

Обычная программная логика контролирует:

* состояние дела;
* переходы между этапами;
* обязательные действия;
* подтверждения;
* задачи;
* сроки;
* права доступа.

Юрист подключается при необходимости и принимает решения в ситуациях, требующих профессиональной проверки.

---

# 2. Главная цель прототипа

Прототип должен позволить заказчику понять:

1. Как пользователь начинает юридическое дело.
2. Как AI проводит интервью.
3. Как из разговора формируются структурированные факты.
4. Как факты связываются с источниками.
5. Как AI предлагает способ решения проблемы.
6. Как пользователь может самостоятельно выполнять действия.
7. Как система ожидает результат действия.
8. Как обрабатывается ответ контрагента.
9. Как дело переходит к следующему этапу.
10. Как готовится досудебная претензия.
11. Как пользователь подтверждает подготовленный документ.
12. Как происходит демонстрационная отправка.
13. Как система реагирует на неудовлетворительный результат.
14. Как начинается подготовка к судебному продолжению.
15. Как дело передаётся юристу.
16. Как юрист проверяет материалы.
17. Как пользователь и юрист могут общаться при нехватке или противоречии данных.
18. Как пользователь может самостоятельно закрыть дело.

Главная задача прототипа — проверить не только внешний вид, но и предлагаемую модель взаимодействия с продуктом.

# 3. Основной демонстрационный сценарий

Создать один основной demo-case, который проходит через максимально большую часть процесса.

Название:

"Возврат денежных средств за неисправный товар"

Категория:

"Защита прав потребителей"

Исходная ситуация:

Пользователь приобрёл бытовую технику. Через некоторое время обнаружил дефект. Пользователь хочет вернуть деньги.

---

# 4. Сценарий основного дела

## Этап 1. Первичное обращение

Пользователь открывает приложение.

Экран должен предложить:

"Опишите, что произошло"

Пользователь вводит mock-сообщение:

"Я купил холодильник, через месяц он перестал нормально работать. Я обратился в магазин, но мне сказали, что сначала нужно провести проверку."

После отправки сообщение становится началом дела.

Система создаёт mock-case.

---

# 5. Этап 2. AI-интервью

AI должен провести заранее подготовленное mock-интервью.

Не подключать настоящий LLM.

Пример диалога:

AI:

"Понял ситуацию. Чтобы определить подходящий способ решения, мне нужно уточнить несколько деталей."

Затем AI задаёт вопросы:

* Когда был приобретён товар?
* Где был приобретён товар?
* Какой именно товар?
* В чём заключается неисправность?
* Когда была обнаружена проблема?
* Обращались ли вы к продавцу?
* Что ответил продавец?
* Какой результат вы хотите получить?
* Есть ли документ, подтверждающий покупку?

Пользователь должен иметь возможность отвечать через mock UI.

Не обязательно реализовывать настоящий свободный диалог.

Можно использовать заранее определённые варианты ответов и кнопки.

При этом интерфейс должен выглядеть как настоящий диалог.

---

# 6. Этап 3. Структурирование фактов

После интервью показать пользователю:

"Что мы узнали"

Например:

| Факт                     | Значение      | Источник     | Состояние                  |
| ------------------------ | ------------- | ------------ | -------------------------- |
| Товар                    | Холодильник   | Пользователь | Подтверждено               |
| Продавец                 | ООО «Техника» | Пользователь | Подтверждено               |
| Дата покупки             | 12.08.2026    | Чек          | Подтверждено документом    |
| Стоимость                | 49 990 ₽      | Чек          | Подтверждено документом    |
| Дата обнаружения дефекта | 15.09.2026    | Пользователь | Подтверждено пользователем |
| Требование               | Возврат денег | Пользователь | Подтверждено               |

Каждый факт должен иметь источник.

Источник может быть:

* сообщение пользователя;
* документ;
* страница документа;
* сообщение юриста.

Важно визуально показать различие между:

"Пользователь сообщил"

и:

"Подтверждено документом".

---

# 7. Этап 4. Рекомендация AI

После интервью AI не должен сразу переходить к претензии.

Он должен предложить возможные варианты решения.

Создать экран:

"Возможные варианты"

Например:

### Вариант 1

"Попробовать решить вопрос напрямую с продавцом"

Описание:

"Вы ещё не направляли продавцу формальное требование. В этой ситуации можно сначала попробовать получить решение без подготовки юридического документа."

Кнопка:

"Попробовать мирное решение"

### Вариант 2

"Подготовить досудебную претензию"

Описание:

"Можно подготовить письменную претензию с изложением обстоятельств и требования о возврате денежных средств."

Кнопка:

"Подготовить претензию"

### Вариант 3

"Обратиться к юристу"

Описание:

"Можно передать материалы юристу для дополнительной оценки ситуации."

Кнопка:

"Передать юристу"

---

# 8. Важное правило AI

Не отображать AI как источник окончательного юридического решения.

Использовать формулировки:

* "Рекомендуемый вариант"
* "Возможный следующий шаг"
* "По имеющимся данным"
* "Требуется дополнительная проверка"

Не использовать:

* "Гарантированно выиграете";
* "Вам точно положена компенсация";
* "Закон однозначно на вашей стороне".

# 9. Этап 5. Мирное урегулирование

Основной demo-flow должен сначала пойти по пути мирного урегулирования.

После выбора:

"Попробовать мирное решение"

создаётся задача:

"Связаться с продавцом и сообщить о проблеме."

Показать:

Ответственный:
Пользователь

Статус:
Ожидаем пользователя

Рекомендуемый срок:
до 10.10.2026

Пользователь нажимает:

"Сообщить результат"

Появляется форма:

"Что произошло?"

В mock-вариантах:

* Продавец согласился решить проблему.
* Продавец отказался.
* Ответ не получен.
* Договориться не удалось.
* Хочу продолжить другим способом.

Для основного demo-case выбрать:

"Продавец отказался."

# 10. Этап 6. Новый анализ ситуации

После результата система должна не просто изменить статус.

Она должна показать:

"Мирное урегулирование не дало результата."

AI предлагает следующий шаг:

"На основании собранных сведений можно подготовить досудебную претензию."

Кнопки:

"Подготовить претензию"

"Обратиться к юристу"

"Закрыть дело"

---

# 11. Этап 7. Подготовка претензии

Перед генерацией документа система должна проверить необходимые данные.

Показать:

"Для подготовки претензии достаточно данных"

или список недостающих данных.

Например:

✓ данные пользователя

✓ данные продавца

✓ сведения о товаре

✓ дата покупки

✓ стоимость

✓ описание дефекта

✓ требования пользователя

✓ подтверждение покупки

Затем:

"Сформировать проект претензии"

---

# 12. Этап 8. Проект претензии

Показать mock document viewer.

Название:

"Претензия продавцу"

Документ должен содержать:

* данные пользователя;
* данные продавца;
* описание покупки;
* описание дефекта;
* обстоятельства обращения к продавцу;
* требование пользователя;
* список приложений.

Рядом показать:

"Документ подготовлен на основании данных дела"

и перечислить использованные факты.

Также показать:

"Документ является проектом и ещё не отправлен."

Кнопки:

"Подтвердить"

"Вернуться к данным"

"Передать юристу"

---

# 13. Этап 9. Подтверждение пользователем

После подтверждения:

Статус:

"Готово к отправке"

Показать:

"Перед отправкой проверьте адресата, содержание документа и приложения."

Добавить mock-чеклист:

✓ Адресат проверен

✓ Содержание проверено

✓ Приложения выбраны

✓ Пользователь подтвердил отправку

---

# 14. Этап 10. Демонстрационная отправка

Отправка должна быть явно обозначена как симуляция.

Например:

"Демонстрация отправки"

"В реальной системе документ будет передан через согласованный юридически значимый канал связи."

Кнопка:

"Имитировать отправку"

После нажатия:

"Документ передан"

Но обязательно:

"Это демонстрационное событие. Реальной отправки не производилось."

Создать событие:

"05.10.2026 — документ передан через демонстрационный канал."

---

# 15. Этап 11. Ожидание ответа

Дело переходит:

"Ожидание ответа"

Показать:

Ожидаем:
"Ответ продавца"

Срок:
"20.10.2026"

Ответственный:
"Продавец"

Добавить кнопку:

"Сообщить о полученном ответе"

Также предусмотреть mock-сценарий:

"Срок истёк, ответа нет."

Для основного demo-case использовать:

"Получен ответ продавца."

---

# 16. Этап 12. Ответ на претензию

Показать документ/сообщение:

"Ответ продавца"

Например:

"В удовлетворении требования отказано."

После просмотра система показывает:

"Ответ не удовлетворяет пользователя."

Возможные действия:

* "Продолжить"
* "Закрыть дело"
* "Обратиться к юристу"

Основной сценарий:

"Продолжить"

---

# 17. Этап 13. Подготовка к судебному продолжению

Теперь начинается отдельная часть процесса.

AI должен показать:

"Для подготовки дела к дальнейшему рассмотрению необходимо собрать дополнительные сведения."

Создать список:

### Уже есть

✓ данные пользователя

✓ сведения о продавце

✓ документы о покупке

✓ претензия

✓ подтверждение отправки

✓ ответ продавца

### Необходимо получить

* дополнительные сведения о товаре;
* подробную историю событий;
* сведения о понесённых расходах;
* дополнительные документы;
* информацию о требованиях пользователя;
* другие данные, необходимые для подготовки искового заявления.

Не утверждать, что именно этот список является юридически исчерпывающим.

Использовать формулировку:

"Демонстрационный список данных, необходимых для подготовки следующего этапа."

---

# 18. Этап 14. Проверка данных

Для каждого факта отображать состояние:

* Подтверждено пользователем
* Подтверждено документом
* Требует уточнения
* Противоречие
* Требуется проверка юриста

Например:

"Дата покупки"

12.08.2026

Источник:
Чек.pdf, стр. 1

Статус:
Подтверждено документом

---

После сбора данных:

"Передать дело юристу"

### Ситуация

### Что произошло

### Документы

Список документов.

### Что было сделано

* обращение к продавцу;
* мирное урегулирование;
* подготовка претензии;
* отправка;
* получен отказ.

### Что предлагает AI

"Подготовить материалы для судебного продолжения."

### Что требует проверки

Список неопределённостей.

Кнопка:

"Передать юристу"

# 20. Этап 16. Интерфейс юриста

Создать отдельный режим приложения:

"Кабинет юриста"

Главный экран:

"Очередь дел"

Для каждого дела показать:

* номер;
* пользователь;
* категория;
* текущий этап;
* причина передачи;
* дата;
* приоритет.

Пример:

| Дело        | Этап                               | Причина            | Статус           |

# 21. Карточка дела юриста

Юрист должен видеть:

Что произошло.

## История

Полный timeline дела.

## Факты

Все собранные факты.

## Источники

Документы и сообщения, на которых основаны факты.

## Документы

Все загруженные и сгенерированные документы.

## Ответ на претензию

Полный mock-ответ.

## Рекомендация AI

Отдельный блок:

"Предложение системы"

Важно визуально отделить его от решения юриста.

## Проблемные места

Например:

⚠️ "Не подтверждена дата обнаружения дефекта."

⚠️ "Требуется уточнить сумму дополнительных расходов."

# 24. Второй demo-case — противоречивые данные

Помимо основного дела создать второе дело.

"Противоречие в данных о покупке"

"Я купил товар 10.08.2026."

"12.08.2026."

⚠️ "Обнаружено противоречие"

Пользователь:
10.08.2026

Чек:
12.08.2026

"Невозможно надёжно определить правильную дату. Требуется уточнение."

"Передать юристу"

# 25. Самостоятельное закрытие дела

На любом этапе, где это логически допустимо, пользователь должен иметь возможность выбрать:

"Закрыть дело"

После нажатия показать подтверждение:

"Вы действительно хотите прекратить сопровождение дела?"

После подтверждения:

Статус:

"Завершено"

Причина:

"Пользователь прекратил работу"

Сохранить это как mock event.

# 26. Модель состояний

Не делать процесс полностью линейным.

Основные этапы:

* Первичное обращение
* Сбор информации
* Анализ ситуации
* Выбор способа решения
* Выполнение действия
* Ожидание результата
* Подготовка претензии
* Согласование
* Отправлено
* Ожидание ответа
* Анализ результата
* Подготовка судебного продолжения
* Проверка юристом
* Завершено

Дополнительные признаки:

* Требуется юрист
* Ожидаем пользователя
* Ожидаем контрагента
* Требуется уточнение
* Обнаружено противоречие
* Ошибка отправки
* Срок требует проверки

# 43. Acceptance criteria

Прототип считается готовым, если:

### Запуск

* `npm install` работает;
* `npm run dev` работает;
* `npm run build` работает;
* нет TypeScript errors.

### Основной сценарий

Пользователь может:

1. Открыть дело.
2. Пройти mock AI-интервью.
3. Увидеть структурированные факты.
4. Увидеть источники фактов.
5. Получить рекомендацию AI.
6. Выбрать мирное урегулирование.
7. Сообщить результат.
8. Получить новую рекомендацию.
9. Запустить подготовку претензии.
10. Просмотреть проект претензии.
11. Подтвердить документ.
12. Увидеть демонстрационную отправку.
13. Увидеть ответ продавца.
14. Указать, что ответ не удовлетворяет.
15. Перейти к подготовке судебного продолжения.
16. Передать дело юристу.

### Юрист

Юрист может:

1. Открыть очередь дел.
2. Открыть дело.
3. Просмотреть историю.
4. Просмотреть факты.
5. Просмотреть источники.
6. Просмотреть документы.
7. Просмотреть рекомендацию AI.
8. Увидеть проблемные места.
9. Написать пользователю.
10. Получить ответ пользователя.
11. Создать запрос дополнительных данных.
12. Принять mock-решение.

### Исключение

Второе demo-case:

1. Содержит противоречивые данные.
2. Показывает оба источника.
3. AI не выбирает значение самостоятельно.
4. Система показывает необходимость уточнения.
5. Пользователь может передать дело юристу.

### Прочее

* пользователь может закрыть дело;
* timeline отражает основные события;
* текущий этап всегда виден;
* следующее действие всегда понятно;
* mock submission явно обозначена как симуляция;
* реальные API отсутствуют;
* API keys отсутствуют;
* приложение пригодно для GitHub Pages.
