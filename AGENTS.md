# AGENTS.md

## 1. Назначение проекта

Этот репозиторий содержит интерактивный frontend-прототип платформы сопровождения юридических дел.

Прототип создаётся для демонстрации заказчику и проверки продуктовой концепции до разработки полноценного приложения.

Подробное функциональное описание и основной demo-flow находятся в:

`docs/prototype.md`

Если требования в этом файле и требования из `docs/prototype.md` противоречат друг другу, приоритет имеют более конкретные требования из `docs/prototype.md`, если они не нарушают архитектурные и технические ограничения, описанные ниже.

---

## 2. Главная цель агента

Твоя задача — реализовать качественный интерактивный прототип, а не production-ready юридическую систему.

Главные критерии качества:

1. Понятный пользовательский сценарий.
2. Понятное состояние юридического дела.
3. Понятный следующий шаг.
4. Наглядное взаимодействие пользователя, AI и юриста.
5. Реалистичные mock-данные.
6. Хороший UX.
7. Возможность показать прототип заказчику без дополнительного объяснения разработчика.

Не следует добавлять сложную техническую инфраструктуру, которая не нужна для демонстрации.

---

# 3. Важный принцип: prototype first

Это frontend-only прототип.

Не реализовывать без явного требования:

* backend;
* базу данных;
* настоящую авторизацию;
* реальные LLM API;
* OCR;
* настоящую загрузку и обработку документов;
* электронную подпись;
* интеграции с судами;
* интеграции с государственными системами;
* реальную отправку юридически значимых документов;
* production workflow engine;
* реальные юридические расчёты.

Если функциональность нужна для демонстрации, использовать mock implementation.

Например:

```text
Real API
   ↓
НЕ реализуем

Mock service
   ↓
Используем
```

---

# 4. Не выдумывать backend

Все данные должны храниться в frontend mock layer.

Не создавать API endpoints только для того, чтобы архитектура выглядела "реалистичнее".

Если в будущем потребуется backend, текущая структура должна позволять заменить mock layer на реальные сервисы без полного переписывания UI.

---

# 5. Основной доменный объект — Case

Центральным объектом приложения является юридическое дело (`Case`).

Не строить архитектуру вокруг отдельных документов.

Документы, сообщения, факты, задачи и события относятся к делу.

Концептуальная структура:

```text
Case
├── Facts
├── Documents
├── Messages
├── Tasks
├── Events
├── Recommendations
├── Actions
├── ExpectedEvents
├── LawyerDecisions
└── Outcome
```

Карточка дела должна позволять восстановить его состояние и историю.

---

# 6. Workflow не должен быть линейным

Не предполагать, что каждое дело проходит один фиксированный путь:

```text
Interview → Claim → Court
```

Дело может переходить между различными маршрутами.

Например:

```text
Interview
    ↓
Analysis
    ↓
┌───────────────┬──────────────┬───────────────┐
│ Self-service  │ Claim        │ Lawyer        │
└───────┬───────┴──────┬───────┴───────┬───────┘
        │              │               │
        └──────────────┴───────────────┘
                       ↓
                    Result
                       ↓
                ┌──────┴──────┐
                │             │
              Solved       Not solved
                │             ↓
              Closed       Next step
```

Нужно предусматривать:

* переход на предыдущий этап;
* повторный сбор информации;
* ожидание результата;
* эскалацию к юристу;
* закрытие дела пользователем;
* дополнительные циклы.

---

# 7. AI не является автономным юристом

AI в прототипе выступает как помощник.

AI может:

* проводить интервью;
* структурировать информацию;
* выявлять недостающие данные;
* выявлять противоречия;
* анализировать предоставленные сведения;
* предлагать возможные варианты действий;
* помогать готовить документы;
* формировать запросы дополнительной информации.

AI не должен изображаться как безусловный источник юридической истины.

Использовать формулировки:

* "Рекомендуемый вариант";
* "Возможный следующий шаг";
* "По имеющимся данным";
* "Требуется дополнительная проверка";
* "Обнаружено противоречие".

Не использовать без необходимости:

* "Вы точно выиграете";
* "Вам гарантированно положена компенсация";
* "Закон однозначно на вашей стороне";
* "Суд обязательно примет решение в вашу пользу".

---

# 8. Решение AI должно быть объяснимым

Если AI предлагает действие, пользователь должен иметь возможность понять, почему оно предложено.

Рекомендация должна быть связана с:

* фактами;
* документами;
* ответами пользователя;
* выявленными обстоятельствами.

Например:

```text
Рекомендуемый следующий шаг:
Подготовить досудебную претензию.

Основания:
• продавец отказался решить вопрос;
• факт покупки подтверждён;
• требование пользователя определено;
• имеется информация о предыдущем обращении.
```

Не показывать необъяснимые рекомендации.

---

# 9. Факты и источники

Факт и его источник — разные сущности.

Например:

```text
Fact:
Дата покупки = 12.08.2026

Source:
Чек.pdf, страница 1
```

или:

```text
Fact:
Дата обращения к продавцу = 20.09.2026

Source:
Сообщение пользователя
```

Не смешивать источник с самим фактом.

Факт должен иметь состояние, например:

* `UNCONFIRMED`
* `CONFIRMED_BY_USER`
* `CONFIRMED_BY_DOCUMENT`
* `CONFLICT`
* `REQUIRES_LAWYER`

Названия enum могут быть другими, если выбранный стиль проекта этого требует.

---

# 10. Противоречивые данные

Если два источника содержат разные значения, AI не должен молча выбирать одно из них.

Например:

```text
Пользователь:
Дата покупки — 10.08.2026

Чек:
Дата покупки — 12.08.2026
```

UI должен показать:

```text
⚠ Обнаружено противоречие
```

и оба источника.

Возможные действия:

* уточнить у пользователя;
* передать юристу.

Это важнее автоматического "исправления" данных.

---

# 11. Expected Event

Текущее состояние дела должно объяснять, почему оно находится в этом состоянии.

Использовать концепцию ожидаемого события.

Например:

```text
Status:
WAITING_FOR_COUNTERPARTY

Expected event:
Ответ продавца

Responsible:
Продавец

Deadline:
20.10.2026
```

Или:

```text
Status:
WAITING_FOR_USER

Expected event:
Предоставить документ

Responsible:
Пользователь
```

Пользователь всегда должен понимать:

* что сейчас происходит;
* кто должен действовать;
* какое действие ожидается;
* есть ли срок.

---

# 12. Timeline

Timeline является важной частью интерфейса.

Он должен показывать ключевые события дела:

```text
Обращение создано
↓
AI-интервью завершено
↓
Рекомендовано мирное урегулирование
↓
Пользователь сообщил результат
↓
Подготовлена претензия
↓
Претензия подтверждена
↓
Отправка
↓
Получен ответ
↓
Начата подготовка судебного продолжения
↓
Дело передано юристу
```

Каждое событие должно по возможности содержать:

* дату;
* описание;
* инициатора;
* источник.

Не хранить историю только как текст внутри компонентов.

---

# 13. Mock data должны быть отделены от UI

Не размещать большие mock-объекты непосредственно внутри React-компонентов.

Предпочтительная структура:

```text
src/
├── data/
│   ├── cases.ts
│   ├── facts.ts
│   ├── documents.ts
│   ├── messages.ts
│   ├── events.ts
│   ├── tasks.ts
│   └── recommendations.ts
│
├── types/
│   └── ...
│
└── features/
    └── ...
```

Компонент должен получать данные через props/state/mock services, а не содержать весь demo-case внутри JSX.

---

# 14. Типизация

Использовать TypeScript.

Основные доменные сущности должны иметь явные типы.

Минимальный набор:

```text
Case
CaseFact
FactSource
Document
DocumentVersion
Message
Task
Event
ExpectedEvent
Recommendation
Action
LawyerDecision
CaseOutcome
```

Не использовать `any`, если можно определить нормальный тип.

Не создавать чрезмерно сложную type system ради прототипа.

---

# 15. Компоненты

Использовать компонентный подход.

Предпочтительная структура:

```text
src/
├── app/
├── pages/
├── components/
├── features/
│   ├── cases/
│   ├── interview/
│   ├── facts/
│   ├── documents/
│   ├── workflow/
│   ├── lawyer/
│   └── messaging/
├── data/
├── types/
└── lib/
```

Не нужно создавать компонент для каждого небольшого `<div>`.

Компонент должен выделяться, если он:

* переиспользуется;
* имеет самостоятельную ответственность;
* содержит сложную логику;
* представляет отдельный элемент интерфейса.

---

# 16. Разделение ответственности

Не смешивать:

* UI;
* domain data;
* mock logic;
* navigation;
* workflow state.

Например:

Плохо:

```text
CasePage.tsx
 ├── огромный mock-case
 ├── все переходы
 ├── вся логика AI
 ├── все сообщения
 └── весь JSX
```

Предпочтительно:

```text
CasePage
   ↓
Case data
   ↓
Feature components
   ↓
Mock actions/services
```

---

# 17. Mock services

Если для взаимодействия требуется асинхронность, использовать mock service.

Например:

```typescript
interviewService.start()
caseService.getCase()
caseService.updateFact()
caseService.submitClaim()
lawyerService.sendMessage()
```

Можно использовать `Promise` и небольшую искусственную задержку.

Это позволит в будущем заменить mock implementation реальным API.

---

# 18. Не создавать искусственную сложность

Это прототип.

Не нужно реализовывать:

* Redux только потому, что это "правильно";
* сложный DI;
* event sourcing;
* CQRS;
* полноценный state machine engine;
* repository pattern для каждого объекта;
* сложную domain-driven architecture.

Если обычного React state/context достаточно — использовать его.

Если состояние действительно становится сложным, выбрать подходящую библиотеку осознанно.

---

# 19. UI должен быть ориентирован на задачу

Главный вопрос каждого экрана:

> "Что пользователь должен понять или сделать здесь?"

На экране дела пользователь должен быстро понять:

```text
Где я?
Что произошло?
Что происходит сейчас?
Что нужно сделать?
Кто должен действовать?
Что будет дальше?
```

Не перегружать интерфейс второстепенной информацией.

---

# 20. AI UI

AI должен быть частью рабочего процесса.

Не делать огромный standalone chatbot, который визуально занимает весь продукт.

AI должен работать в контексте дела.

Например:

```text
Case
├── Situation
├── Current status
├── Next action
├── Facts
├── Documents
└── AI assistant
```

AI должен иметь возможность ссылаться на:

* факты;
* документы;
* события.

---

# 21. Lawyer UI

Юрист должен видеть не только текущий документ.

Он должен получать контекст дела:

```text
Case
├── Summary
├── Timeline
├── Facts
├── Sources
├── Documents
├── AI recommendation
├── Problems
└── Communication
```

Рекомендация AI и решение юриста должны визуально различаться.

---

# 22. Роли

Настоящей authentication/authorization в прототипе нет.

Использовать mock role switcher:

```text
Пользователь
Юрист
```

Режим юриста должен показывать соответствующий интерфейс.

Всегда явно обозначать prototype/mock режим.

---

# 23. Дизайн

Стиль:

* professional;
* clean;
* calm;
* trustworthy;
* modern legal-tech.

Избегать:

* неоновых цветов;
* чрезмерных градиентов;
* "роботизированного" AI-дизайна;
* чрезмерных анимаций;
* визуального шума.

AI не должен выглядеть как рекламный gimmick.

---

# 24. Accessibility

Не полагаться только на цвет.

Для состояний использовать:

* текст;
* иконку при необходимости;
* цвет как дополнительный сигнал.

Интерактивные элементы должны иметь понятные labels.

Кнопки должны явно описывать действие.

Например:

Хорошо:

```text
Передать дело юристу
```

Плохо:

```text
Продолжить
```

если из контекста непонятно, что произойдёт.

---

# 25. Responsive

Основная целевая платформа:

desktop.

Особенно для кабинета юриста.

Но пользовательский интерфейс должен оставаться usable на:

* tablet;
* mobile.

Не нужно добиваться pixel-perfect mobile версии, если это мешает скорости разработки прототипа.

---

# 26. GitHub Pages

Приложение должно работать на GitHub Pages.

Учитывать:

* static hosting;
* отсутствие backend;
* base path;
* отсутствие серверных rewrite rules.

Предпочтительно использовать routing, совместимый с GitHub Pages.

Если используется React Router, предпочтительно рассмотреть `HashRouter`, если нет убедительной причины использовать другую стратегию.

---

# 27. Не использовать реальные секреты

Никогда не добавлять в repository:

* API keys;
* tokens;
* passwords;
* credentials;
* реальные персональные данные.

Даже если для prototype потребуется mock API key — лучше полностью отказаться от него.

---

# 28. Реальные данные

Использовать только synthetic/mock data.

Не добавлять:

* реальные ФИО клиентов;
* реальные адреса;
* реальные телефоны;
* реальные документы;
* реальные паспортные данные;
* реальные юридические дела.

---

# 29. Документы

Документы в прототипе являются mock entities.

Не требуется реальный PDF/DOCX processing.

Можно использовать:

* mock document viewer;
* заранее подготовленный текст;
* placeholder preview.

Всегда явно обозначать, если действие является симуляцией.

Например:

> "Это демонстрационная отправка. Реального документа отправлено не было."

---

# 30. Юридические ограничения прототипа

Прототип не должен создавать впечатление гарантированного юридического результата.

Не использовать формулировки, которые создают ложную уверенность.

Если необходимо показать юридическую рекомендацию, использовать:

> "Демонстрационная рекомендация AI"

или:

> "Возможный вариант действий"

---

# 31. Код должен быть понятным

Предпочитать:

* понятные имена;
* небольшие компоненты;
* очевидные зависимости;
* простые решения.

Не оптимизировать код преждевременно.

Но и не создавать одноразовый код, который будет невозможно развивать после прототипа.

---

# 32. Перед изменением архитектуры

Если для реализации новой функции требуется существенно изменить архитектуру:

1. Сначала объяснить проблему.
2. Предложить простой вариант.
3. Предложить альтернативу, если она действительно нужна.
4. Выбрать решение, соответствующее масштабу прототипа.

Не внедрять крупные архитектурные изменения молча.

---

# 33. Перед реализацией новой функции

Проверить:

1. Есть ли соответствующее требование в `docs/prototype.md`.
2. Можно ли реализовать функцию через mock.
3. Не добавляет ли она ненужную production complexity.
4. Не ломает ли существующий demo-flow.

Если требование не определено, предпочитать минимальное решение.

---

# 34. Работа с требованиями

Если требования неоднозначны:

* не придумывать сложную бизнес-логику;
* выбрать наиболее простой вариант, совместимый с текущим UX;
* при существенной неоднозначности сообщить о ней до реализации.

Не заменять требования собственными предположениями без необходимости.

---

# 35. Работа с существующим кодом

Перед изменением существующего кода:

1. Изучить текущую структуру.
2. Найти существующие компоненты.
3. Переиспользовать существующие решения, если они подходят.
4. Не переписывать работающий код без необходимости.

Не создавать дубликаты компонентов.

---

# 36. Проверка после изменений

После существенных изменений выполнить:

```bash
npm run build
```

Если в проекте существуют:

```bash
npm run lint
npm run test
```

также выполнить их.

Исправить все ошибки TypeScript/build.

Не считать задачу завершённой, если проект не собирается.

---

# 37. Проверка demo-flow

Перед завершением работы пройти основной сценарий вручную:

```text
Landing
↓
New case
↓
Situation
↓
AI interview
↓
Facts
↓
Recommendation
↓
Peaceful resolution
↓
User reports failure
↓
Claim
↓
Claim preview
↓
Confirmation
↓

↓
Waiting
↓
Counterparty response
↓
Unsuccessful result
↓
Court preparation
↓
Lawyer
↓
Lawyer requests information
↓
```

---

# 38. Не считать mock-данные частью бизнес-логики

Demo-case должен быть заменяемым.

Например, не писать:

```typescript
if (case.id === "LC-2026-001") {
   // весь workflow
}
```

Лучше описывать состояние через данные:

```typescript
case.status
case.stage
case.expectedEvent
case.availableActions
```

Такой подход позволит в будущем добавить другие дела.

---

# 39. Принцип progressive disclosure

Не показывать пользователю всю информацию сразу.

Сначала:

```text
Что произошло?
```

# 43. Definition of Done

Работа считается завершённой, когда:

* приложение запускается локально;
* production build проходит;
* основной demo-flow полностью проходим;
* lawyer-flow полностью проходим;
* contradiction-flow работает;
* пользователь может закрыть дело;
* mock data отделены от UI;
* основные сущности типизированы;
* timeline отображает историю;
* текущий этап дела понятен;
* следующее действие понятно;
* AI и юрист визуально различаются;
* mock actions явно обозначены;
* приложение пригодно для демонстрации заказчику;
* GitHub Pages deployment не требует backend.

# 44. Принцип для агента

Главное правило:

> Не пытайся построить полноценную юридическую платформу. Построй убедительный, понятный и интерактивный прототип, который позволяет заказчику проверить концепцию продукта.

Если приходится выбирать между:

```text
сложная архитектура
```

и

```text
понятный работающий demo-flow
```

для этого этапа выбирай:

```text
понятный работающий demo-flow
```

Но при этом не создавай архитектурных решений, которые без необходимости сделают последующее развитие проекта невозможным.
