# AGENTS.md

## 1. Назначение проекта

Этот репозиторий содержит интерактивный frontend-прототип сервиса отправки
досудебных претензий через Почту России (ИС ЭПС — Электронные Заказные Письма).

Прототип создаётся для демонстрации заказчику и проверки продуктовой концепции до
разработки полноценного приложения.

Подробное функциональное описание и основной demo-flow находятся в:

`docs/prototype2.md`

Если требования в этом файле и требования из `docs/prototype2.md` противоречат друг
другу, приоритет имеют более конкретные требования из `docs/prototype2.md`, если они
не нарушают архитектурные и технические ограничения, описанные ниже.

---

## 2. Главная цель агента

Твоя задача — реализовать качественный интерактивный прототип, а не production-ready
сервис отправки почты.

Главные критерии качества:

1. Понятный пользовательский сценарий (загрузка PDF → указание адресата → проверка →
   демонстрация отправки → отслеживание статуса).
2. Понятное состояние отправления.
3. Понятный следующий шаг.
4. Наглядное взаимодействие пользователя с сервисом.
5. Реалистичные mock-данные (синтетические имена, адреса, идентификаторы).
6. Хороший UX.
7. Возможность показать прототип заказчику без дополнительного объяснения разработчика.

Не следует добавлять сложную техническую инфраструктуру, которая не нужна для
демонстрации.

---

## 3. Важный принцип: prototype first

Это frontend-only прототип.

Не реализовывать без явного требования:

* backend;
* базу данных;
* настоящую авторизацию;
* реальные LLM API;
* OCR;
* настоящую загрузку и обработку документов;
* электронную подпись;
* реальная интеграция с ИС ЭПС (API Почты России);
* реальные платежи;
* реальная отправка писем.

Если функциональность нужна для демонстрации, использовать mock implementation.

Например:

```text
Real API (ИС ЭПС)
    ↓
НЕ реализуем

Mock service
    ↓
Используем
```

---

## 4. Не выдумывать backend

Все данные должны храниться в frontend mock layer (localStorage для черновиков,
синтетические данные для demo-отправлений).

Не создавать API endpoints только для того, чтобы архитектура выглядела "реалистичнее".

Если в будущем потребуется backend, текущая структура должна позволять заменить mock
layer на реальные сервисы без полного переписывания UI.

---

## 5. Основной доменный объект — Shipment (отправление)

Центральным объектом приложения является почтовое отправление (`Shipment`).

Документ, отправитель, получатель, статус, история событий относятся к отправлению.

Концептуальная структура:

```text
Shipment
├── Sender
├── Recipient
├── Document
├── Status
├── Events
└── ExpectedEvent
```

Карточка отправления должна позволять восстановить его состояние и историю.

---

## 6. Workflow не должен быть линейным

Не предполагать, что каждое отправление проходит один фиксированный путь.

Основной сценарий:

```text
Dashboard
    ↓
New shipment
    ↓
Step 1: Upload document
    ↓
Step 2: Sender & recipient
    ↓
Step 3: Verification
    ↓
Step 4: Demo sending
    ↓
Result
```

Необходимо предусмотреть:

* переход на предыдущий шаг мастера;
* возврат к редактированию черновика;
* возврат к списку черновиков;
* удаление черновика с подтверждением;
* сохранение черновика при переходах между шагами.

---

## 7. Mock implementation вместо реальной отправки

AI/сервис в прототипе выступает как помощник.

Сервис может:

* проверять формат загружаемого файла (PDF);
* валидировать обязательные поля формы;
* генерировать синтетический номер отправления (ШПИ);
* симулировать последовательность статусов;
* отображать демонстрационную историю событий.

Сервис не должен изображаться как безусловный источник правды о реальной отправке.

Использовать формулировки:

* "Демонстрационный режим. Письмо не отправлено";
* "Синтетический номер отправления";
* "Демонстрационный статус доставки";

Не использовать без необходимости:

* "Письмо отправлено";
* "Доставка гарантирована";
* "Скорее всего доставят завтра".

---

## 8. Объяснимость demo-операций

Если сервис симулирует статус, пользователь должен иметь возможность понять, почему
такой статус назначен.

Статус должен быть связан с:

* историей событий;
* данными формы;
* состоянием отправителя/получателя.

---

## 9. Факты и источники

В прототипе используются синтетические данные. Факт и его источник — разные сущности.

Например:

```text
Fact:
Адрес получателя = 644077, Омская обл., г. Омск, пр. Мира, д. 57, кв. 66

Source:
Введено пользователем
```

или:

```text
Fact:
ФИО получателя = Иванов Иван Иванович

Source:
Заполнено из профиля отправителя
```

Не смешивать источник с самим фактом.

---

## 10. Противоречивые данные

Если два источника содержат разные значения, UI должен показать:

```text
⚠ Обнаружено противоречие
```

и оба источника.

Это важнее автоматического "исправления" данных.

---

## 11. Expected Event (Ожидаемое событие)

Текущее состояние отправления должно объяснять, почему оно находится в этом
состоянии.

Использовать концепцию ожидаемого события.

Например:

```text
Status:
В пути

Expected event:
Подтверждение доставки получателем

Responsible:
Получатель

Deadline:
20.10.2026
```

Или:

```text
Status:
Требует внимания

Expected event:
Исправить данные отправителя

Responsible:
Пользователь
```

---

## 12. Timeline

Timeline является важной частью интерфейса. Он должен показывать ключевые события
отправления:

```text
Документ добавлен
↓
Отправитель и получатель заполнены
↓
Отправление проверено
↓
Демонстрационная операция завершена
↓
Принято системой
↓
В пути
↓
Вручено
```

Каждое событие содержит:

* дату;
* описание;
* инициатора;
* пометку "демонстрационное".

---

## 13. Mock data должны быть отделены от UI

Не размещать большие mock-объекты непрямую внутри React-компонентов.

Предпочтительная структура:

```text
src/
├── data/
│   ├── sender.ts          # Профиль отправителя
│   └── shipments.ts       # Demo-отправления
├── types/

│   └── labels.ts          # Russian labels
├── features/
│   └── shipment/          # Shipment components
├── pages/
├── components/
├── lib/
│   └── shipmentService.ts # Mock service
└── styles/
```

## 17. Mock services

Для асинхронных операций использовать mock service.

```typescript
shipmentService.createDraft()

shipmentService.getShipments()
```

---

## 18. Не создавать искусственную сложность

Это прототип.

Не нужно реализовывать:

* Redux только потому, что это "правильно";
* сложный DI;
* event sourcing;
* CQRS.

Если обычного React state/Context достаточно — использовать его.

---

## 19. UI должен быть ориентирован на задачу

Главный вопрос каждого экрана:

> "Что пользователь должен понять или сделать здесь?"

На экране отправления пользователь должен быстро понять:

```text
Где я?
Что произошло?
Что происходит сейчас?
Что нужно сделать?
Кто должен действовать?
Что будет дальше?
```

## 20. Использование документации API Почты России

Документы `docs/Pamyatka_API_otpravitelya_IS_EPS_cfa50e1b73.pdf` и
`docs/Pamyatka_API_poluchatelya_IS_EPS_b2fec82643.pdf` описывают реальный API ИС ЭПС.

Используйте их для:

* понимания структуры данных (Sender, Recipient, AddressStruct, Document, Charge);
* названий полей (postalCode, region, city, street, houseNumber, corpus, flat, countryCodeOKSM);
* статусов API (UNKNOWN, ACCEPTED, IN_PROGRESS, ONLINE_DELIVERED, DELIVERED_TO_PRINT, FAILED);
* понимания ограничений (PDF/A-1, максимум 5 МБ, портретная ориентация, А4);
* кодов разряда (mailRank: 4 — судебное, 8 — административное и т.д.);
* типов отправления (REGULAR, REGISTERED);
* формата ШПИ (Штриховой Почтовый Идентификатор).

**Важно**: не реализовывать реальную интеграцию. Использовать сведения только для
правдоподобности mock-данных и понятности интерфейса.

## 33. Definition of Done

Работа считается завершённой, когда:

* приложение запускается локально;
* production build проходит;
* основной demo-flow полностью проходим (Dashboard → New shipment → 4 steps → Result);
* пользователь может сохранить черновик и продолжить;
* пользователь может открыть, удалить черновик;
* настройки профиля сохраняются и используются при создании новых отправлений;
* список отправлений поддерживает поиск и фильтрацию;
* карточка отправления показывает согласованные данные и историю;
* timeline отображает историю;
* текущий статус отправления понятен;
* следующее действие понятно;
* mock data отделены от UI;
* основные сущности типизированы;
* mock actions явно обозначены как демонстрационные;
* приложение пригодно для демонстрации заказчику;
* GitHub Pages deployment не требует backend.
